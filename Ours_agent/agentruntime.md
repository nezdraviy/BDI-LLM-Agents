# AgentRuntime — библиотека для создания агентов

**Участник 1** реализует общий механизм управления агентом: получение задачи, выбор целей и планов, выполнение шагов и пересмотр решений.

Документ предназначен для разработчиков, которые будут подключать свои компоненты. Требуется Python 3.11+, внешних зависимостей при выполнении нет.

## Кто за что отвечает

| Участник | Компонент | Что делает |
| --- | --- | --- |
| Участник 1 | `AgentRuntime` | Управляет выполнением: выбирает план, запускает шаги, обрабатывает ошибки и изменения |
| Участник 2 | `profile: AgentProfile` | Хранит знания, предоставляет цели и планы, проверяет условия и достижение целей |
| Участник 3 | `proposals: ProposalProvider` | При необходимости предлагает недостающий план; может использовать LLM |
| Участник 4 | `executor: ActionExecutor` | Выполняет действия через реальные инструменты и возвращает наблюдения |

`profile` — знания и правила конкретного агента. `executor` — исполнитель его действий. Подключив другие профиль и инструменты, можно создать другого агента на том же runtime.

## Как проходит выполнение

```text
Задача → знания → оценка целей → выбор плана → выполнение шага
            ↑                                      ↓
            └──────── обновление знаний ← наблюдения
```

1. Runtime получает `Task` и запрашивает текущие знания у профиля.
2. Профиль возвращает цели и сообщает, какие уже достигнуты.
3. Runtime выбирает незавершённую цель и применимый план. Больший `priority` выбирается раньше; при равенстве используется порядок `id`.
4. Перед следующим шагом проверяются условия, поддержка действий и актуальность знаний.
5. Исполнитель выполняет действие и возвращает `ActionResult`.
6. Профиль принимает наблюдения через `integrate()`. Runtime переходит к следующему шагу и повторяет цикл.
7. Когда профиль подтверждает достижение всех текущих целей, задача завершается успешно.

Например: задача — проверить файл; цель — получить подтверждённый результат проверки; план — прочитать файл, проверить поля, сохранить отчёт; намерение — выполнять этот план, начиная со второго шага.

Runtime сам не извлекает цели из текста задачи. Предметные правила задаёт профиль. **Выполнение всех шагов ещё не означает успех: достижение цели проверяется отдельно.**

## Как запустить

Ниже функция, принимающая готовые компоненты остальных участников:

```python
from agent_runtime import (
    ActionExecutor, AgentProfile, AgentRuntime,
    ProposalProvider, RunResult, Task,
)


async def process(
    profile: AgentProfile,
    executor: ActionExecutor,
    proposals: ProposalProvider | None = None,
) -> RunResult:
    task = Task(
        id="validation-001",
        description="Проверить входные данные",
        payload={"source_path": "data/input.csv"},
    )
    runtime = AgentRuntime(
        profile=profile,
        executor=executor,
        proposals=proposals,
    )
    return await runtime.run(task)
```

Ключ `source_path` условный: структуру `payload` согласуют приложение и профиль. В примере не реализованы реальные проверки или инструменты.

Один экземпляр runtime выполняет одну задачу за раз. Методы с `async` вызываются через `await`.

## Основные методы runtime

| Метод | Вход | Результат |
| --- | --- | --- |
| `AgentRuntime(profile, executor, proposals=None, limits=None)` | Готовые компоненты и необязательные ограничения | Экземпляр в состоянии `IDLE` |
| `start(task)` | `Task` | `None`; начинает новую сессию, состояние `RUNNING` |
| `await run(task)` | `Task` | Итоговый `RunResult`; самостоятельно запускает и выполняет цикл |
| `await tick()` | Без аргументов, после `start()` | `RuntimeStatus`; выполняет не более одного действия |
| `cancel()` | Без аргументов | `None`; запрашивает отмену |
| `result()` | Без аргументов, после `start()` | `RunResult` на текущий момент |

Для ручного управления используйте `start(task)`, затем вызывайте `await tick()`, пока `state == RuntimeStatus.RUNNING`. После последнего действия может понадобиться ещё один цикл для подтверждения достижения целей.

`run(task)` всегда начинает новую сессию; он не продолжает сессию после ручного `start()`. Параллельные `run()` и `tick()` на одном экземпляре запрещены.

Для наблюдения доступны свойства:

- `state: RuntimeStatus` — текущее состояние;
- `events: tuple[Event, ...]` — журнал событий;
- `intentions: tuple[Intention, ...]` — история намерений.

## Форматы данных

Методы обмениваются **Python-объектами**, а не JSON-словарями. Все модели импортируются из `agent_runtime`. `Mapping[str, object]` обычно передаётся как `dict`, последовательности — как `list` или `tuple`.

### Задачи, цели и планы

| Объект | Основные поля |
| --- | --- |
| `Task` | `id: str`, `description: str`, `payload: Mapping[str, object] = {}` |
| `BeliefSnapshot` | Объект с атрибутом `revision: str`; остальные поля знаний определяет профиль |
| `Goal` | `id: str`, `priority: int = 0` |
| `Plan` | `id: str`, `goal_id: str`, `steps: tuple[Step, ...]`, `priority: int = 0` |
| `Step` | `id: str`, `action: str`, `parameters: Mapping[str, object] = {}` и настройки попыток ниже |
| `Context` | `task: Task`, `beliefs: BeliefSnapshot`, `goal: Goal` |

`Task.payload` содержит входные данные или ссылки на них. `Step.action` — имя действия, которое понимает исполнитель, а `parameters` — его параметры.

У `Step` есть дополнительные настройки:

| Поле | По умолчанию | Значение |
| --- | --- | --- |
| `timeout_seconds: float \| None` | `None` | Таймаут попытки; `None` использует общий таймаут |
| `max_retries: int` | `0` | Число дополнительных попыток |
| `retry_safe: bool` | `False` | Разрешено ли повторять действие |
| `retry_delay_seconds: float` | `0` | Задержка перед повтором |

Например, описание плана — только данные, а не реализация инструментов:

```python
from agent_runtime import Plan, Step

plan = Plan(
    id="validate-v1",
    goal_id="validation-complete",
    steps=(
        Step(id="read", action="read_source"),
        Step(id="check", action="check_fields"),
    ),
)
```

### Проверки, действия и предложения

| Объект | Поля и смысл |
| --- | --- |
| `Check` | `allowed: bool`, `reason: str = ""` — можно ли использовать план или шаг |
| `GoalAssessment` | `status: GoalStatus`, `reason: str = ""` — оценка цели |
| `ActionRequest` | `context: Context`, `intention_id: str`, `plan_id: str`, `step: Step`, `attempt: int`, `idempotency_key: str` — запрос инструменту |
| `ActionResult` | `observations: Mapping[str, object] = {}` — наблюдения инструмента |
| `PlanningGap` | `context: Context`, `rejected_plans: tuple[str, ...]`, `reason: str` — описание отсутствующего решения |
| `PlanProposal` | `plan: Plan`, `explanation: str = ""` — предложенный план |

`GoalStatus` принимает `PENDING` — цель не достигнута, `ACHIEVED` — достигнута, `IMPOSSIBLE` — недостижима. Передавайте элемент перечисления, например `GoalStatus.ACHIEVED`, а не строку `"achieved"`.

`attempt` начинается с `1` для каждого шага. `idempotency_key` имеет вид `"{intention_id}:{step.id}"` и сохраняется между повторами. Исполнитель отвечает за применение этого ключа к реальному инструменту.

Схему `observations` согласуют профиль и исполнитель. Runtime передаёт её без предметного разбора. Отсутствие обязательного поля в данных может быть обычным результатом проверки; технический сбой инструмента сообщается исключением `ActionError`.

### Отчёт и история

| Объект | Поля |
| --- | --- |
| `RunResult` | `task: Task`, `status: RuntimeStatus`, `reason: str`, `belief_revision: str \| None`, `cycles: int`, `actions: int`, `replans: int`, `events: tuple[Event, ...]`, `intentions: tuple[Intention, ...]` |
| `Event` | `sequence: int`, `kind: str`, `details: Mapping[str, object]` |
| `Intention` | `id: str`, `goal_id: str`, `plan_id: str`, `status: IntentionStatus`, `next_step: int = 0`, `attempts: int = 0`, `reason: str = ""` |

`next_step` — индекс следующего шага с нуля. `attempts` относится к текущему шагу и сбрасывается после его успеха. Состояния намерения: `ACTIVE`, `SUSPENDED`, `SUCCEEDED`, `FAILED`, `DROPPED`, `CANCELLED`.

Журнал фиксирует начало задачи, выбор и завершение намерений, действия, повторы, пересмотр и завершение задачи. `sequence` начинается с `1`; временной метки нет.

`RunResult` можно получить и во время выполнения через `result()`. Он содержит последнюю наблюдавшуюся версию знаний, но не весь снимок и не все ответы инструментов. Предметный результат, например файл отчёта, хранит профиль или исполнитель.

## Что должен реализовать участник 2: `profile`

Все методы асинхронные. Кроме `integrate()`, они читают состояние без его изменения.

| Метод и вход | Выход | Назначение |
| --- | --- | --- |
| `observe(task: Task)` | `BeliefSnapshot` | Получить актуальный снимок знаний |
| `goals(task: Task, beliefs: BeliefSnapshot)` | `Sequence[Goal]` | Получить текущие обязательные цели |
| `assess_goal(context: Context)` | `GoalAssessment` | Проверить достижение одной цели |
| `plans(context: Context)` | `Sequence[Plan]` | Получить планы для `context.goal` |
| `plan_applicable(plan: Plan, context: Context)` | `Check` | Проверить условия плана при принятии и продолжении |
| `step_applicable(step: Step, context: Context)` | `Check` | Проверить условия следующего шага |
| `integrate(request: ActionRequest, result: ActionResult)` | `None` | Принять наблюдения и обновить знания |
| `validate_proposal(proposal: PlanProposal, context: Context)` | `Check` | Проверить предметную корректность предложенного плана |

Три важных правила:

- Снимок знаний неизменяем. При изменении фактов, целей, приоритетов или планов профиль выдаёт новую непустую строку `revision`. По ней runtime обнаруживает устаревшее решение.
- Все возвращённые цели обязательны. Удаление ID из следующего списка означает отзыв цели. Сохраняйте достигнутые обязательные цели в списке до конца задачи; пустой список даёт `BLOCKED`.
- `plan_applicable()` проверяет условия, которые должны сохраняться во время всего плана. Условия только для начала размещайте в проверке первого шага.

ID целей и планов в одном ответе должны быть уникальны. `plan.goal_id` должен совпадать с запрошенной целью. Для изменённого описания плана используйте новый ID.

## Что должен реализовать участник 4: `executor`

| Метод и вход | Выход | Назначение |
| --- | --- | --- |
| `supports(action: str)` | `bool` | Быстро и синхронно проверить поддержку действия |
| `await execute(request: ActionRequest)` | `ActionResult` | Выполнить `request.step.action` с его `parameters` |

Техническую ошибку нужно возбуждать через `raise ActionError(message, retryable=False)`. Для временной ошибки можно указать `retryable=True`.

Порядок успешного шага: `execute()` → `ActionResult` → `profile.integrate()` → следующий шаг. Обычная ошибка интеграции завершает задачу: уже выполненное действие автоматически не повторяется.

## Что должен реализовать участник 3: `proposals`

Метод `await propose(gap: PlanningGap)` возвращает `PlanProposal` или `None`, если решения нет.

Он вызывается, когда библиотека не дала применимого плана. Предложение проверяют профиль, условия плана и список поддерживаемых действий. Вложенные `Plan` и `Step` должны быть Python-объектами; разбор ответа LLM выполняет этот компонент.

Компонент необязателен: при `proposals=None` используются планы профиля. `validate_proposal()` вызывается только при получении структурно подходящего предложения. Для одной пары «цель, revision» допускается не более одного запроса, также действует общий лимит.

## Изменения, ошибки и ограничения

Если условия изменились, runtime пересматривает решение. Более приоритетная применимая цель может приостановить текущее намерение между шагами; затем оно продолжается с сохранённой позиции после проверки условий.

Повтор действия разрешён только одновременно при `retry_safe=True`, `ActionError(retryable=True)` и оставшихся `max_retries`. У повторов сохраняются намерение и ключ идемпотентности.

Если повтор невозможен, runtime отбрасывает план и ищет альтернативу. Проваленный план исключается до конца запуска. План, потерявший применимость, может рассматриваться заново после изменения `revision`.

| Параметр `RuntimeLimits` | По умолчанию | Что ограничивает |
| --- | --- | --- |
| `max_cycles` | `100` | Циклы выбора и исполнения |
| `max_actions` | `100` | Попытки действий, включая повторы |
| `max_replans` | `20` | Пересмотры после отказа от принятого плана |
| `max_gap_requests` | `2` | Запросы предложений на весь запуск |
| `hook_timeout_seconds` | `10` | Секунды на один асинхронный вызов профиля или поставщика предложений |
| `action_timeout_seconds` | `30` | Секунды на одну попытку действия |

Передайте настройки через `AgentRuntime(..., limits=RuntimeLimits(...))`. Таймаут шага может переопределить общий. При `max_retries > 0` обязательно `retry_safe=True`; `max_gap_requests=0` отключает запросы предложений.

Таймаут действия допускает повтор только по указанным правилам. Обычные ошибки профиля, интеграции или поставщика предложений завершают задачу как `FAILED`.

Отмена и таймаут кооперативны: адаптеры должны поддерживать асинхронную отмену. Они не гарантируют откат уже выполненного внешнего действия. При ручном режиме после `cancel()` нужен следующий или уже выполняющийся `tick()` для фиксации отмены. Внешняя отмена asyncio-задачи обычно пробрасывает `CancelledError`; если уже вызван `runtime.cancel()`, он подавляется.

## Состояния выполнения

| `RuntimeStatus` | Значение |
| --- | --- |
| `IDLE` | Задача ещё не запущена |
| `RUNNING` | Выполняется |
| `SUCCEEDED` | Все текущие цели подтверждены как достигнутые |
| `BLOCKED` | Нет целей или применимого продолжения без предшествующего провала |
| `FAILED` | Невозможная цель, ошибка компонента, превышение лимита или отсутствие продолжения после провалов |
| `CANCELLED` | Выполнение отменено |

`BLOCKED` завершает текущий запуск; автоматического ожидания новых данных нет. После терминального состояния можно начать новую задачу. История runtime сбрасывается, а состояние подключённых компонентов остаётся их ответственностью.

## Что важно при интеграции

- ID должны быть непустыми; шаги плана — непустой последовательностью `Step` с уникальными ID.
- Модели защищены от изменения полей, а отображения — только на верхнем уровне. Вложенные значения также нужно сохранять неизменными.
- JSON автоматически не преобразуется в модели и обратно. Для внешнего сообщения явно создавайте объекты; для вывода выбирайте поля и используйте `.value` у перечислений.
- Намерения и история хранятся в памяти. Автоматического восстановления после перезапуска нет.
- Подробности внутренних методов смотрите в `agent_runtime/runtime.py`; точные определения полей — в `models.py`, интерфейсы компонентов — в `contracts.py`.
