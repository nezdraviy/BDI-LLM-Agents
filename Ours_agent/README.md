# Общий runtime агента

Python-библиотека для части проекта, за которую отвечает наша команда: архитектура и жизненный цикл агента, выбор целей и планов, управление намерениями, выполнение шагов и пересмотр решений. Python 3.11 или новее; внешних зависимостей при выполнении нет.

Runtime не содержит предметной логики обработки и проверки данных. Первый агент подключается через контракты, которые могут использовать и другие агенты.

Запускаемая сборка первого агента теперь находится в `first_agent/`: она соединяет
этот runtime, `DataValidationProfile` и реальные инструменты `data_tools` участника 4.
Инструкция, примеры и описание заглушек — в [FIRST_AGENT.md](FIRST_AGENT.md).
Оставшиеся задачи и ответственные — в [FIRST_AGENT_TODO.md](FIRST_AGENT_TODO.md).

Быстрый запуск из этой папки без установки:

```powershell
python -B run_first_agent.py --source examples/first_agent/input --output reports/first-agent
```

## Разделение ответственности

| Участник | Ответственность | Точка подключения |
| --- | --- | --- |
| Наша команда | Цикл управления, выбор целей и планов, намерения, ошибки, повторы, пересмотр, отмена, лимиты, журнал | `AgentRuntime` |
| Человек 2 | Модель beliefs, факты, цели, библиотека планов, предусловия, критерии достижения, проверка предложений | `AgentProfile`, `BeliefSnapshot` |
| Человек 3 | Контекст LLM, запросы, структурированные предложения для конкретного пробела | `ProposalProvider` |
| Человек 4 | Разрешённые действия, обёртки инструментов, наблюдения, демонстрационный запуск и экспериментальная оценка | `ActionExecutor` |

В проекте есть профиль проверки данных, инструменты чтения LAS/CSV/TSV,
базовые проверки и синтетический стенд. В новой сборке предметные правила,
связи между файлами, окончательный допуск, LLM и восстановление представлены
явными заглушками. Базовые unit-тесты runtime используют doubles; тесты сборки
первого агента читают настоящие временные файлы и проверяют сохранённые отчёты.

## Архитектура

- `agent_runtime/models.py` — общие сообщения и неизменяемые описания: задача, цель, план, шаг, намерение, результаты и лимиты.
- `agent_runtime/contracts.py` — протоколы интеграции с остальными участниками.
- `agent_runtime/runtime.py` — управление выполнением.
- `tests/` — unit-тесты runtime.

`Task` задаёт задачу. `BeliefSnapshot` предоставляет текущую версию знаний, которую runtime не интерпретирует. `Goal` описывает цель и её приоритет; `Plan` содержит упорядоченные `Step`. `Intention` фиксирует принятое решение выполнять конкретный план и хранит курсор следующего шага.

Контейнеры моделей защищены от изменения на верхнем уровне. Вложенные значения в `Task.payload`, `Step.parameters` и наблюдениях принадлежат адаптерам: они должны оставаться неизменными во время использования. Снимок beliefs должен быть неизменяемым; изменение знаний требует новой `revision`.

## Жизненный цикл

1. `start(task)` начинает новую задачу. `run(task)` выполняет этот же цикл автоматически.
2. Runtime получает актуальный снимок через `profile.observe(task)`, список целей и оценку их достижения.
3. Цели рассматриваются по убыванию `priority`; равный приоритет разрешается по возрастанию `id`. Все цели текущего списка обязательны. Пустой список целей даёт `BLOCKED`, а не успех.
4. Для незавершённой цели runtime получает планы, проверяет их применимость и выбирает план по убыванию `priority`, затем по `id`. Из выбранного плана создаётся намерение.
5. Перед действием проверяются актуальность плана и предусловия шага. Поддерживаемое исполнителем действие передаётся в `executor.execute(request)`.
6. Наблюдения из `ActionResult` передаются в `profile.integrate(request, result)`. Следующее наблюдение и оценки используют актуальные знания.
7. Применимая цель с более высоким приоритетом может приостановить текущее намерение. После её обработки намерение продолжается с сохранённого курсора, если план по-прежнему применим.
8. Утрата применимости или ошибка ведёт к пересмотру решения и отбрасыванию соответствующего намерения. Runtime может выбрать другой план в пределах лимитов.
9. Если подходящего плана нет, необязательный `ProposalProvider` получает `PlanningGap`. Возвращённый `PlanProposal` проходит `profile.validate_proposal`, обычные проверки применимости и проверку поддержки действий. Предложение остаётся данными; runtime не исполняет сгенерированный Python-код.
10. `SUCCEEDED` выставляется только тогда, когда `profile.assess_goal` возвращает `GoalStatus.ACHIEVED` для всех целей текущего списка. Завершение списка шагов само по себе успехом не считается.

Результат `profile.goals` задаёт авторитетный текущий набор целей. Профиль может добавить цель или явно отозвать её, удалив ID из следующего списка. Намерение отозванной цели отбрасывается; её достижение больше не требуется. Если обязательство должно сохраняться до завершения всей задачи, профиль обязан сохранять эту цель в списке, в том числе после её достижения.

| Состояние | Значение |
| --- | --- |
| `IDLE` | Задача ещё не запущена |
| `RUNNING` | Задача выполняется, возможно дальнейшее продвижение через `tick()` |
| `SUCCEEDED` | Профиль подтвердил достижение всех целей текущего списка |
| `BLOCKED` | Профиль не предоставил целей или применимого плана, позволяющего продолжить выполнение |
| `FAILED` | Недостижимая цель, ошибка адаптера, исчерпанный бюджет или провал планов без доступного продолжения |
| `CANCELLED` | Выполнение остановлено по отмене |

Причина завершения, счётчики и история намерений доступны в `RunResult`. Повторный или конкурентный запуск активного экземпляра недопустим; для параллельных задач используйте отдельные экземпляры и адаптеры с подходящей изоляцией состояния.

## Контракты интеграции

`AgentProfile` предоставляет:

| Метод | Назначение |
| --- | --- |
| `observe(task)` | Вернуть текущий неизменяемый снимок beliefs |
| `goals(task, beliefs)` | Вернуть авторитетный текущий список обязательных целей; отсутствие ранее возвращённого ID означает отзыв цели |
| `assess_goal(context)` | Оценить цель: `PENDING`, `ACHIEVED` или `IMPOSSIBLE` |
| `plans(context)` | Вернуть планы для цели |
| `plan_applicable(plan, context)` | Проверить применимость плана |
| `step_applicable(step, context)` | Проверить предусловия шага |
| `integrate(request, result)` | Интерпретировать наблюдения и обновить собственное состояние знаний |
| `validate_proposal(proposal, context)` | Проверить предложенный план по правилам профиля |

Все методы профиля асинхронны. Кроме `integrate`, они не должны изменять состояние. Идентификаторы целей, планов и шагов должны сохранять смысл на протяжении задачи.

`plan_applicable` проверяет инварианты, которые должны выполняться и при принятии плана, и при его продолжении после любого шага или приостановки. Условия, нужные только для входа в план, следует проверять через `step_applicable` первого шага: иначе успешный первый шаг может сделать весь план неприменимым для собственного продолжения. Предусловия каждого следующего шага оцениваются на момент его исполнения.

`ActionExecutor.supports(action)` — быстрая синхронная проверка разрешённого действия. Асинхронный `execute(request)` возвращает `ActionResult` либо сообщает об ошибке. Реальные блокирующие функции требуют асинхронного адаптера со стороны исполнителя.

`ProposalProvider.propose(gap)` асинхронно возвращает `PlanProposal` либо `None`. Компонент необязателен: без него runtime работает с библиотекой планов профиля.

## Подключение готовых компонентов

Установка из этой папки:

```powershell
python -m pip install -e .
```

Функция интеграции принимает реализации других участников. Она не создаёт предметный профиль, инструменты или LLM-компонент:

```python
from agent_runtime import (
    ActionExecutor,
    AgentProfile,
    AgentRuntime,
    ProposalProvider,
    RunResult,
    RuntimeLimits,
    Task,
)


async def process_task(
    task: Task,
    profile: AgentProfile,
    executor: ActionExecutor,
    proposals: ProposalProvider | None = None,
) -> RunResult:
    runtime = AgentRuntime(
        profile=profile,
        executor=executor,
        proposals=proposals,
        limits=RuntimeLimits(
            max_cycles=100,
            max_actions=100,
            max_replans=20,
            max_gap_requests=2,
            hook_timeout_seconds=10,
            action_timeout_seconds=30,
        ),
    )
    return await runtime.run(task)
```

Для встраивания в собственный цикл управления:

```python
from agent_runtime import AgentRuntime, RunResult, RuntimeStatus, Task


async def process_stepwise(runtime: AgentRuntime, task: Task) -> RunResult:
    runtime.start(task)
    while runtime.state == RuntimeStatus.RUNNING:
        await runtime.tick()
    return runtime.result()
```

`tick()` возвращает текущий `RuntimeStatus`. `state`, `events` и `intentions` позволяют наблюдать выполнение. `cancel()` запрашивает кооперативную отмену; вызывающий код продолжает цикл до терминального состояния.

## Ошибки, повторы и ограничения

Повтор действия разрешён только при `Step.retry_safe=True` и ошибке `ActionError(retryable=True)`. Таймаут действия runtime преобразует в такую повторяемую ошибку; флаг `retry_safe` по-прежнему обязателен. `max_retries` ограничивает дополнительные попытки, `retry_delay_seconds` задаёт задержку. Один логический шаг получает стабильный `idempotency_key` между повторами; исполнитель отвечает за его применение к реальному инструменту.

`RuntimeLimits` задаёт бюджеты на одну задачу:

| Параметр | По умолчанию | Что ограничивается |
| --- | --- | --- |
| `max_cycles` | `100` | Циклы выбора и исполнения, включая циклы, решение которых устарело до отправки действия |
| `max_actions` | `100` | Вызовы исполнителя, включая неудачные попытки и повторы |
| `max_replans` | `20` | Пересмотры после отброса плана; после превышения лимита новый план не выбирается |
| `max_gap_requests` | `2` | Общее число запросов предложений; `0` отключает их |
| `hook_timeout_seconds` | `10` | Время одного асинхронного вызова профиля или поставщика предложений, в секундах |
| `action_timeout_seconds` | `30` | Время одной попытки действия, в секундах |

Оценка достижения целей выполняется до проверки бюджетов: последнее разрешённое действие может завершить задачу. Один `tick()` отправляет не более одного действия, а после последнего действия для подтверждения успеха нужна следующая оценка целей. Запрос предложения для одной пары «цель, revision beliefs» выполняется не более одного раза. `Step.timeout_seconds` позволяет задать таймаут отдельного действия вместо общего `action_timeout_seconds`.

Отмена и таймаут не доказывают, что внешний побочный эффект был отменён. Кооперативная отмена требует, чтобы адаптеры корректно обрабатывали отмену асинхронной операции. Runtime не предоставляет постоянное хранилище, восстановление после перезапуска или гарантию выполнения действия ровно один раз.

Журнал содержит события управления и идентификаторы, без полного содержимого задачи, параметров действий и наблюдений. Полные предметные данные и их хранение остаются ответственностью адаптеров.

## Проверка

Из корня `Ours_agent`:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q agent_runtime
```

Тесты runtime проверяют управление жизненным циклом, детерминированный выбор,
критерии успеха, намерения, пересмотр, ошибки, повторы, предложения, таймауты и
отмену. `test_first_agent.py` дополнительно проверяет настоящую связку на временных
LAS/CSV, сохранение отчётов, ошибки и CLI. Отдельные тесты инструментов находятся
в `participant4-tools/tests/`. Ответы настоящей LLM и инженерная пригодность
данных этими тестами не подтверждаются.
