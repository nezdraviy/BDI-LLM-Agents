# Первый агент: проверка входных файлов

Сборка объединяет существующие `AgentRuntime`, `DataValidationProfile` и
`DataValidationExecutor`. Сейчас она выполняет базовую техническую проверку LAS и
CSV. Предметные правила оставлены явными заглушками: даже чистый технический
отчёт содержит `admission.status = "not_assessed"` и не разрешает моделирование.

## Запуск

Нужен Python 3.11 или новее. Команды выполняются из папки `Ours_agent`.
Для запуска исходников установка пакета не требуется:

```powershell
python -B run_first_agent.py --source examples/first_agent/input --output reports/first-agent
```

Тот же пример с явно указанной политикой-заглушкой:

```powershell
python -B run_first_agent.py --source examples/first_agent/input --output reports/first-agent --policy examples/first_agent/policy.stub.json
```

После установки пакета доступна команда:

```powershell
python -m pip install --no-deps .
first-data-agent --source examples/first_agent/input --output reports/first-agent
```

| Параметр | Назначение |
| --- | --- |
| `--source PATH` | Файл или папка входных данных |
| `--output PATH` | Папка результатов; отдельный подкаталог для каждого запуска |
| `--policy PATH` | Необязательный JSON с настройками `ValidationPolicy` |
| `--task-id ID` | Необязательный идентификатор; без него создаётся новый для каждого запуска |
| `--no-recursive` | Читать только указанную папку, без вложенных папок |
| `--action-timeout SECONDS` | Ограничить время одного действия |

Нейтральные примеры содержат поля `DEPT, VALUE` в LAS и `ID, VALUE` в CSV.
Они проверяют маршрут обработки, без геологических норм и утверждённых диапазонов.

## Результат

Результаты сохраняются в `--output/<task-id>/`:

- `validation.json` — структурированный отчёт: инвентаризация и находки проверок;
- `validation.md` — читаемая версия отчёта;
- `result.json` — итог запуска, ссылки на отчёты, статус допуска и явные заглушки.

В `_runtime/validation.json` может находиться исходный отчёт исполнителя.
Он отделён от итоговых файлов сборки: завершившаяся после таймаута фоновая запись
не должна перезаписать диагностический отчёт и список заглушек.

| Код завершения | Значение |
| --- | --- |
| `0` | Runtime завершился успешно, базовые проверки не нашли ошибок; предупреждения возможны |
| `1` | Найдены технические ошибки данных либо ни один файл не удалось передать проверкам |
| `2` | Сбой выполнения или некорректная конфигурация запуска |

Код `0` и runtime-статус `succeeded` описывают выполнение технической проверки.
Пока предметный допуск не реализован, `admission.status` всегда `not_assessed`.
Если часть файлов не поддерживается, а другие успешно проверены, результат
будет `warnings`, код — `0`; непрочитанные файлы явно перечислены в отчёте.
Повреждённый поддержанный файл создаёт ошибку и код `1`.

## Как работает сборка

```text
CLI: source + policy + output
  → новая задача и отдельное состояние запуска
  → AgentRuntime выбирает цели и планы DataValidationProfile
  → scan_source_directory
  → parse_input_files
  → validate_input_data
  → build_validation_report → save_validation_report
  → validation.json + validation.md + result.json
```

Инструменты читают LAS 1.2/2.0 и CSV, проверяют структуру, пустые данные,
повторяющиеся имена полей, пустые кривые, монотонность глубины LAS и соответствие
её границ заголовку. Обязательные поля и числовые диапазоны берутся из политики.
В `policy.stub.json` оба набора правил пустые. Исходные файлы не исправляются.

Runtime отвечает за цикл выполнения; профиль — за цели, планы и оценку результата;
инструменты — за чтение, проверки и отчёт. Заглушка LLM возвращает `None` вместо
предложения плана. Пропущенные предметные возможности перечислены в результате
запуска и в [FIRST_AGENT_TODO.md](FIRST_AGENT_TODO.md).

## Текущие границы

- Метаданные CRS, datum, единицы и словари мнемоник не нормализуются. Числовой
  диапазон сам по себе не подтверждает правильность единиц.
- Связи между файлами, идентификаторы скважин и полнота проектного комплекта
  пока не проверяются. Политика задаёт поля по формату, без отдельных схем для
  разных видов LAS или CSV.
- Основной профиль пока выполняется без автоматических повторов действий.
  Сбой не запускает скрытую подмену данных или альтернативный предметный план.
- Состояние не восстанавливается после завершения процесса. Повторный запуск —
  новый проход чтения и проверки с новым идентификатором; это не resume.
- Настоящий LLM-провайдер и предметный допуск остаются заглушками.
- Счётчик `validated` означает передачу прочитанного файла базовым проверкам.
  Полный перечень выполненных и пропущенных проверок отдельных полей пока
  отсутствует и отмечается заглушкой `per_check_coverage`.
